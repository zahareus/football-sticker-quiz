# StickerHunt 3.0: специфікація фаз 0 і 1 (без коду й екранів)

**Статус:** ЧЕРНЕТКА 2026-10-25. Основа: `03-synthesis-structure.md` (прийнято Віктором). Усі факти про схему перевірені запитами до прод-бази 25.10 (лише читання). Нічого в проді не змінювалось.
**Правила виконання (з CLAUDE.md репо):** міграції застосовує Віктор через Management API, НЕ `supabase db push`; кожна нова таблиця = RLS + явні GRANT + тест; жодних anon-політик запису; кожна міграція має скрипт відкату й перевірочні запити; перед кожним кроком premortem + diff + «так» Віктора; на безпеку: `/claude-security` (запускає лише Віктор).

## 0. Факти, на яких стоїть специфікація (перевірено 25.10)
- `profiles`: колонки `id` (FK на `auth.users`), `username`, `updated_at`, `can_upload` (default false), `can_edit` (default false). **SELECT дозволений усім (public) по всіх колонках.** Клієнт пише в профілі тільки `username`, `updated_at` і вставляє новий рядок (`id`, `username`, `updated_at`).
- Запис у `stickers`/`clubs` і в storage: лише `authenticated` з `profiles.can_upload`; UPDATE за `can_edit`. Anon-запису нема (міграція 006).
- Тригер у БД один: `clubs_changed_webhook` (AFTER INSERT OR UPDATE на `clubs`) → n8n → генерація сторінок. **Тригерів на `stickers` нема.**
- RPC, відкриті anon: `get_battle_pair`, `submit_vote`, `increment_sticker_views`, `record_quiz_answer`, `get_sticker_rank`, `get_percentile_rank` (усі SECURITY DEFINER).
- `stickers.club_id` NOT NULL; колонки автора нема; 0 неактивних стікерів; квіз не фільтрує `active`.
- Шлях аплоаду: `upload.js` кладе в Storage СИРИЙ файл (`selectedFile`), EXIF читається окремо (exifr) лише для метаданих; `upload-batch.js` так само. Серед оригіналів 1837 із 4723 прочитаних у форматі MPO (iPhone multi-picture).

## 1. Крок 0.0: закрити самонадання прав (терміново, окремо від структури)
**Знайдено:** за каталогом прав роль `authenticated` має UPDATE на `profiles` включно з колонками `can_upload` і `can_edit`; політика оновлення перевіряє лише `auth.uid() = id`; політика вставки профілю теж перевіряє тільки `id`; тригерів на `profiles` нема. **За цими даними будь-хто з Google-входом може виставити собі `can_upload=true` (і `can_edit=true`), тобто «за запрошенням» зараз обходиться.** Експлуатацію записом НЕ перевіряв (Supabase MCP лише для читання); висновок із прав і політик. Серпневий аудит згадував «акаунти без can_upload», але цієї дороги не описав.
**Що змінити (міграція 008):** (а) забрати в `authenticated` і `anon` право UPDATE на колонки `can_upload`, `can_edit` (лишити UPDATE лише `username`, `updated_at`); (б) обмежити INSERT профілю: дозволені колонки `id`, `username`, `updated_at`, а політика вимагає, щоб `can_upload` і `can_edit` не були true; (в) CHECK на `username` (довжина й набір символів), бо аудит називав XSS через нік.
**Перевірка після (читання):** `has_column_privilege('authenticated','public.profiles','can_upload','UPDATE')` = false; політика вставки містить умову; Вікторів профіль має `can_upload=true` і `can_edit=true` без змін.
**Ручна перевірка Віктором (запис):** нік змінюється (профіль), новий акаунт створює профіль, Віктор і далі завантажує стікер.
**Ризик:** якщо хтось уже самонадав собі права, це видно в `select * from profiles where can_upload or can_edit`; перевірити ДО міграції й вирішити, що робити з тими акаунтами.
**Це окремий 🔴 пункт: його варто робити першим, навіть якщо структуру 3.0 відкласти.**

## 3. Фаза 1: дані
**Принципи:** жодна нова таблиця не відкрита для прямого запису з клієнта; усі записи через функції SECURITY DEFINER із перевіркою форми вхідних даних, ліміту частоти й прапорця в `settings`; EXECUTE лише потрібним ролям; `search_path` зафіксований (як у міграції 007).

**Спотери (автори).** ВАЖЛИВО: `profiles` читається всіма по всіх колонках і прив'язана до `auth.users`, тому **прапорець «сіяний» не можна класти в `profiles`** (він був би публічним) і сіяні персони не можуть бути профілями. Рішення:
- Таблиця `spotters`: `id uuid PK`, `handle` (унікальний, лише `[a-z0-9_]`), `display_name`, `home_city`, `avatar_url`, `user_id` (nullable, FK на `profiles` для реальних людей), `is_seed boolean`. **Прямого читання цієї таблиці немає ні в кого, крім service role.**
- Вид `spotters_public`: `id, handle, display_name, home_city, avatar_url` (без `is_seed`, без `user_id`); GRANT SELECT лише на вид для anon/authenticated.
- `stickers.spotter_id uuid REFERENCES spotters(id)` (nullable; NULL = «архів»). Колонку читає будь-хто (це лише uuid).
- Клієнтський шар показує «Spotted by @handle» через RPC `get_sticker_card(p_id)` (повертає spotter, лічильник ♥, чи є в «збережених» тощо), без прямого доступу до таблиць.

**♥.** Таблиця `likes(sticker_id FK, voter_key text CHECK форми, created_at, PRIMARY KEY (sticker_id, voter_key))` без прямих grants; RPC `toggle_like(p_sticker_id, p_voter_key)`: перевірка форми ключа (як `user_recent_session_id_shape`), ліміт N ♥ за годину на ключ, прапорець `likes_enabled`; лічильник `stickers.like_count` оновлюється в тій самій функції (насичення, як у `increment_sticker_views`). «Топ по клубу» показується від 3 ♥. Сиди не ♥ (клієнтів немає, у RPC не потрібна окрема логіка).

**Маю/хочу.** Для анонімів лише `localStorage` (на сервері нічого). Для залогінених таблиця `collection(user_id → profiles, sticker_id, kind CHECK in ('have','want'), created_at, UNIQUE(user_id, sticker_id))`; RPC `sync_collection(p_items jsonb)` з обмеженням розміру пакета (≤200), записує тільки під `auth.uid()`.

**Скарги.** Таблиця `reports(id, sticker_id, voter_key, reason CHECK, created_at)`; RPC `report_sticker`. Автоприховування НЕ вмикаємо (квіз не фільтрує `active`, а помилковий розподіл скарг відкрив би брігейдинг): при ≥3 різних ключах ставиться `needs_review` і Віктор отримує сповіщення в Telegram; рішення за ним.

**Клуби від внесників.** `clubs.created_by uuid` (nullable) і `clubs.verified boolean NOT NULL DEFAULT true` (додавання колонки з константним дефолтом НЕ запускає тригер `clubs_changed_webhook`; **не робити масового UPDATE `clubs`**, бо кожен рядок запустить webhook і регенерацію). Новий клуб від не-Віктора вставляється з `verified=false`; функція `notify_club_changed` пропускає неперевірені, тож сторінка не генерується і сторінки його стікерів теж; Віктор схвалює в `/mod.html`, що ставить `verified=true` і одним UPDATE запускає звичайну генерацію.

## 4. Фаза 1: клієнтські зміни (без екранів, тільки поведінка)
- Спільний `shared.js` підвантажує `settings`; кожна функція показується лише коли її прапорець true; за відсутності відповіді нічого не показуємо (статична сторінка лишається повною).
- Резерв місця під динамічні блоки в `style.css`, щоб CLS ≤ 0.1 (перевірка Android-емуляцією до розгортання).
- Форма додавання: **кнопка відправки неактивна без вибраного клубу** (закриває відомий борг «рядок без клубу мовчки пропускається»); «post as» вибір спотера лише для `can_edit`; вимикач `uploads_enabled`; після відправки статус «публікується» (генерація триває хвилини).
- Жодних змін статичних шаблонів і генераторів до SEO-гейту.

## 5. Порядок міграцій
008 закрити самонадання прав → 009 `settings` → 010 `spotters` + вид → 011 `stickers.spotter_id`, `like_count`, тригер округлення → 012 `likes` + `toggle_like` → 013 `collection` + `sync_collection` → 014 `reports` + `report_sticker` → 015 `clubs.created_by/verified` + оновлена `notify_club_changed`. Кожна: `BEGIN/COMMIT`, скрипт відкату, перевірочні запити, окремий коміт (≤100 рядків), `/claude-security` на 008–015 одним проходом перед ввімкненням прапорців.

## 6. Атрибуція наявних 4783 стікерів (окремий крок, масова операція)
UPDATE `stickers.spotter_id` пакетами по ~200 (тригерів на `stickers` нема, статика не чіпається, `reconcile-stickers` перевіряє наявність файлів, а не автора). Правило: за містом із `location` (кластери Лісабон/Амстердам/…) призначається персона цього міста (3–8 персон на великий кластер), без рандомізатора; стікери без міста лишаються за «головним» спотером Віктора. Персони створює Віктор (імена, міста); EXIF існуючих оригіналів не чіпаємо (див. R6). Перед запуском: рішення Віктора про рядок в About.

## 7. Тести (мінімум)
- RLS/права: anon не читає `spotters`, не пише ніде; `authenticated` без `can_upload` не вставляє стікер/клуб/файл; після 008 жоден `authenticated` не змінює `can_upload`/`can_edit`.
- RPC: форма `voter_key`, ліміти, вимкнений прапорець повертає без запису; `sync_collection` пише лише під своїм `auth.uid()`.
- Генератори: сторінка стікера зі `spotter_id` рендериться ТАК САМО (статичний HTML без змін) — corpus-guard `test:placeholders` зелений.
- E2E (Playwright): клієнтський шар не ламає сторінку без JS; CLS ≤ 0.1; ♥ і маю/хочу працюють анонімно.
- Аплоад: exiftool на файлі в Storage без GPS/Make/DateTime; кнопка без клубу неактивна.

## 8. Premortem: що найімовірніше піде не так
1. **008 заблокує легітимний вхід** (якщо код десь пише `can_upload` у профіль): перевірено, клієнт пише лише `username`/`updated_at`; усе одно тест на двох акаунтах до закриття вікна.
2. **Масовий UPDATE `clubs`** запустить шторм регенерацій і повторить травневий інцидент: заборонено; колонки з дефолтом без UPDATE.
3. **Зачистка EXIF зіпсує орієнтацію або якість** (MPO, HEIC): тест на вибірці з усіх форматів до ввімкнення для зовнішніх; Віктор може лишитися на старому шляху.
4. **Клієнтський шар у `shared.js` (кеш 4 год) зламає 4783 сторінки одним релізом:** розгортати за прапорцем `settings` і спершу на клубах з 10+ стікерами; відкат = змінити значення прапорця.
5. **Профілі-персони викриваються за іншими слідами** (час додавання, мова): прийняти як ризик, зменшувати розкидом часу публікації й різними містами.
6. **Нові таблиці без GRANT/RLS** (уроки 15.08): кожна міграція має тест прав.
